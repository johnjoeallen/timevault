## Findings about the existing code

- The project is Rust, not Java; there is no `WalkDir` and no SQLite dependency yet.
- Staging, atomic publish and same-day replacement recovery already exist in `src/backup/generation.rs`.
- Cascade is a star. Downstream job failures are reported without aborting other disks; only mount and lock errors abort.
- The previous generation is already the job's own `current` symlink on each disk, so rotation gaps work today.
- `current` is updated by remove-then-symlink, which is not atomic (fixed in Phase 2).
- The primary disk is the first connected disk in config order.
- `run_backup_job` writes its excludes file to `$HOME/tmp/timevault.<job>.excludes`, which blocks safe full-run tests.
- `cargo fmt --check` already failed on `main` (formatting drift in `generation.rs` and a few test lines in `mod.rs`).
- `run_pristine_only` does take the per-job lock (an early concern that it did not was wrong).
- `<disk>/.timevault` is a YAML identity file at the disk root (`src/disk/identity.rs`).
- Without `--cascade`, only each job's primary disk receives a backup; a second connected disk gets nothing.
- Each job's primary is the first eligible connected disk allowed for it, in `backupDisks` order (not `diskIds` order).
- rsync exit 24 maps to `Success` (`status_for_rsync_code`); the `Partial` status is currently unused by that path.
- Bug (fixed in 1.14.2): with `--disk-id <id> --cascade`, cascade targets came from all connected disks and were not filtered for `disabled`. Decision D10 below.
- Same-size, same-second edits are invisible to rsync's quick check; tests must change file length or mtime.

### Phase 3: skip-by-default and `--recreate` (1.15.0, feature)

- **Behaviour change (D1):** a backup day that already has a completed generation on a disk is skipped and reported `already complete`: `check_existing_target` runs right after the job lock, before the remote host is woken, so no wake, hooks, rsync, retention or `current` change happens. Interruption cleanup (`recover_interrupted`, `repair_current`) runs first, so completeness is judged on the repaired state and a cascade reads a correct `current`. "Complete" = carries `.timevault-complete`, or is what `current` points at (covers generations from before the marker); any other directory with the day's name is treated as an old release's partial and replaced as before.
- **Flag (D2):** `--recreate`, alias `--refresh`, global like the other options, plumbed through `BackupOptions.recreate`. Listed in `--help`; documented in the User Guide (the CI flag check failed until it was).
- **`BackupJobStatus::AlreadyComplete`:** new status (`already complete`, blue in the HTML report). `produced_snapshot()` is true for it, so a job already complete on the primary still cascades to disks that lack the day, and a downstream disk that has it reports `already complete` too.
- **Recreate references:** `generation::link_dest_refs` returns the `--link-dest` list. Normal runs: `[current]` as before. Recreating the day `current` points at: `[previous marked generation, existing target]`; no earlier generation: `[existing target]`. `run_rsync` now takes a list and emits one `--link-dest` per entry. The existing target is only read; the swap and old-copy removal reuse the Phase 2 exchange publication, so a failed or interrupted rebuild keeps the old generation.
- **Guard:** recreate fails with `refusing to recreate <day>: newer generation <x> exists` when any newer generation directory is present. The flag takes no date, so a historical day cannot be named; the guard covers clock changes and injected days.
- **Test seam (closes an open item):** `util::paths::scratch_dir()` replaces the hard-coded `$HOME/tmp` for the excludes file and redirects into the test lock directory under `cfg(test)`, so tests can drive the real `run_backup_for_day` without writing into the real home directory.
- **Tests (+12, 206 total):** second run skipped and untouched; skip repairs `current` after a crash between publish and `current`; recreate rebuilds only the current day and leaves history bit-identical; recreate creates an absent day; recreate links against the previous generation and reuses the old target (inode assertions); failed recreate leaves the generation intact (source removed); crash after the exchange during recreate resolves to a complete generation; recreate refuses an older day; partial directory from an old release is not complete; reference-list selection cases; `--recreate`/`--refresh` parsing; `AlreadyComplete` cascades. Disabling the skip makes the skip test fail.
- **Docs:** new `docs/recreate.md`; updates to `architecture.md`, `cascade.md`, `recovery.md`, `retention-capacity.md` (the "one generation per day" paragraph described the old replace behaviour), `design-rationale.md`, `examples.md`, README and the User Guide (options, Backup command with the behaviour-change note, Snapshot generations). `recreate.md` is in the deb assets.

Notes and limits:
- Behaviour change for users who run a job more than once a day: the generation now keeps the state of the first run unless `--recreate` is used.
- `--recreate` applies to every disk in a run, including downstream cascade disks.
- A recreate with no completed target behaves like a normal run.
- Not exercised against a real mounted disk or a real SSH source; the tests drive `run_backup_for_day` on directories.
- `cargo fmt --check` is clean again (the drift on `main` was fixed as a side effect of reformatting `generation.rs` in Phase 2).

### Phase 4: disk-local SQLite index (1.16.0, feature)

- **Module:** `src/backup/index.rs`; dependency `rusqlite` with the `bundled` feature (no new runtime package for the deb). Database at `<disk>/.timevault/index/file-index.sqlite` (D8), relative paths stored as BLOBs so non-UTF-8 names round-trip.
- **Schema:** `meta` (schema version), `generations` (per job and role: generation name, marker token, file count), `files` (per job, role and path: name, kind, size, mtime_ns, dev, ino, nlink, mode, uid, gid; indexed by name+size, size and inode), `hashes` keyed by `(ino, size, mtime_ns, algo, version)` with provenance (`hashed_at`, `source`). The disk is one filesystem, so the inode alone identifies a file within it; `dev` is stored for information only, because device numbers can change between mounts.
- **Lifecycle:** `Session` (the only thing the backup path uses) runs `prepare` (reuse or rebuild "previous", clear leftover "current"), `record` (walk the finished staging tree after the marker is written), `commit` (after publish, one transaction: drop old "previous", relabel "current", purge unreferenced hashes) and `abandon` (failed run). Reconciliation after a crash needs no journal: "previous" is trusted only if its generation name, marker token and row count match the reference generation, otherwise it is rebuilt from the disk.
- **Lookups for Phase 5:** by path, by name and size, by size, by hash (with a different name), all files of a role, hard-link groups, same-inode test.
- **Hashing:** lazy SHA-256 via the existing `sha2` crate, shared between hard links, trusted only after the file's size, mtime and inode are re-checked (before and after reading); otherwise `Stale`. `ctime` is not used because hard-linking changes it.
- **Failure policy:** every index step on the backup path is best effort. Errors become warnings and switch the index off for the run; a corrupt database is moved aside (`.corrupt-<n>`, newest kept) and rebuilt; a newer schema is left untouched.
- **Bug found by repeated test runs and fixed:** with several jobs opening a fresh database together, `PRAGMA journal_mode=WAL` returned `SQLITE_BUSY` immediately without honouring the busy timeout, which would have skipped the index for a run in production. Setup is now retried until the busy timeout passes. 0 failures in 80 full runs and 100 isolated runs after the fix (about 1 in 15 before).
- **Config:** `options.index` (default false) plumbed to `BackupOptions.index`; example config and User Guide updated. Job names starting with `.timevault` are now rejected so a job cannot collide with files Timevault keeps at the disk root.
- **Tests (+27; 233 run plus 1 ignored benchmark):** 18 index unit tests (relative paths only, non-UTF-8 names, lookups, lazy and shared hashing, staleness by content, mtime, inode and removal, lifecycle advance, failed run, reuse and rebuild conditions, missing index, corrupt index, newer schema, jobs isolated, four parallel jobs on one database, inert session, unusable index) and 8 end-to-end tests through `run_backup_for_day` (index follows published generations with history bit-identical, failed run, crash between publish and index update then reconciled, deleted index, corrupt index, unusable index, not created unless enabled, recreate, two jobs on one disk) plus the reserved-name test. Two mutations were confirmed caught: disabling the staleness check and skipping the commit.
- **Benchmark (ignored test `bench_index_100k_files`, release, warm cache, 100,000 files):** full build 0.44 s; reuse check 2 ms; record plus commit 0.96 s; name+size lookup 3.5 ms; bare walk and stat 0.08 s; database 50 MB (about 500 bytes per file).
- **Docs:** `architecture.md` (new "Disk-local file index" section and layout), `recovery.md` (missing or corrupt index), `retention-capacity.md` (index space), `design-rationale.md`, User Guide (`options.index`, reserved job names), example config.

Notes and limits:
- Nothing consumes the index yet; enabling it only adds cost until Phase 5.
- `record` walks the whole new generation and `commit` relabels every row, so cost scales with total files, not changed files. Before Phase 5 enables it by default, consider keying rows by generation (so commit is O(1)) and recording only changed files from rsync's output. The database is about 500 bytes per file; trimming indexes would shrink it.
- Extended attributes and ACLs are not captured, so Phase 5 must not treat the index as proof that those match.
- Timing is for a warm cache on local storage; a cold cache on a spinning disk will be slower, as it is for rsync.
- Not exercised on a real removable disk or on filesystems without WAL support (the default journal would be used there).

### Phase 5: relocation-aware reuse (1.17.0, feature)

- **Module:** `src/backup/relocation.rs`. Off by default (D16): `options.relocation` is `true`/`false` or a block (`enabled`, `minSize` 65536, `maxChanges` 200000, `timeoutSeconds` 900, `verify` auto|hash|size-mtime); a job can override with `relocation: true|false`. It switches the file index on.
- **Pipeline (D17):** (1) dry run of the real rsync command (same excludes and user options, plus `--delete --delete-excluded`, `TZ=UTC`, `--out-format=%i|%l|%M|%n`) against the previous generation yields new files (`>f+++++++++`) and vanished files (`*deleting`); names are unescaped from rsync's `\#NNN` form. (2) Pair them using the disk-local index (D18). (3) Hard-link each match at its new path under `<job>/.timevault-reloc`. (4) Run the real rsync with that directory as an extra `--link-dest`. (5) Remove it, also on failure; `recover_interrupted` removes leftovers.
- **Pairing evidence:** local source (including cascade): files are grouped by size and mtime, each group is hashed once in one transaction, and pairs are made by equal SHA-256 plus equal mode; also finds duplicates of files that still exist. Remote source: only a unique move (vanished old path, one new file of the same size and mtime, unique both ways); with `verify: hash` each pairing is then confirmed by rsync's checksum (D15). Ambiguous groups, too-small files and attribute mismatches are left to rsync.
- **Safety:** the shadow directory is only ever a read-only reference for rsync, so no inode shared with a completed generation can be written (tested with a moved file whose mode changed: new storage, old mode and inode intact). Never fails a backup: every problem is a "skipped" note; an index error switches the index off for the run.
- **Bail-outs:** more new+vanished files than `maxChanges`, planning past `timeoutSeconds`, a failing dry run, or an unavailable index all abandon relocation for the run with a log line.
- **Performance bug found by the benchmark and fixed:** the first matcher tried only 8 candidates per new file. On a mass rename of 20,000 files that share a size class and mtime it took 55.7 s and reused nothing. It now hashes each size+mtime group once and pairs by content: 1.26 s, 9.6 MiB extra instead of 157 MiB. A 300-file regression test pins it.
- **Benchmark** (`bench_relocation`, ignored test; local FS, warm cache, release, 20,000 files of about 4 KiB): no change 0.30 s plain vs 0.55 s with relocation (0.8 vs 5.3 MiB incl. index); every folder moved 0.36 s, 157 MiB vs 1.24 s, 10.6 MiB; every file renamed 0.37 s, 157 MiB vs 1.26 s, 9.6 MiB. **Not measured:** the extra dry-run pass over SSH, any remote workload, cold caches or spinning disks.
- **Tests (+46; 279 run plus 2 ignored benchmarks):** parsing of rsync's output (escapes, pipes in names, directories, symlinks); config resolution and YAML forms; matching (moved directory, rename, move plus rename, unique remote move, ambiguous groups decided by content, look-alike rejected, copies shared only when verified, mode mismatch, minimum size, non-UTF-8 names, 300 identical-size files); limits (change limit, expired time limit, failing dry run); shadow construction failures and cleanup; rsync-checksum confirmation (classification, remote move linked, look-alike rejected, mixed set, mode change, hostile file names with spaces, newline, quotes, `$(...)` and non-UTF-8 bytes, failing run); and end to end through `run_backup_for_day` (bulk move, control without relocation, mass rename, move plus rename, permission change keeps history intact, edited after move, look-alike, change between planning and copying, change limit, failed run cleans up, leftover shadow removed, unusable index, default minimum size, per-job override, safe mode, cascade stage). Disabling content verification makes the look-alike tests fail, which shows the data corruption it prevents.
- **Docs:** new `docs/relocation.md`; updates to `architecture.md`, `retention-capacity.md`, `cascade.md`, `recovery.md`, `design-rationale.md`, User Guide (options, job key, Snapshot generations), README and the example config. `relocation.md` is in the deb assets.

Notes and limits:
- (Changed in 1.18.0, see below.) The 1.17.0 remote default trusted any unique move by size and mtime.
- Remote duplicates (copies of files that still exist) and ambiguous remote groups are not detected.
- rsync reports mtimes in whole seconds, so matching is at second resolution, which is also what its own quick check uses.
- Statistics are logged, not yet in the email report.
- The index's record-and-commit cost (about 1 s per 100,000 files) applies whenever relocation is on; keying rows by generation and recording only changed files remains a possible optimisation.

### Phase 5 follow-up: verification refinements (1.18.0, feature)

- **Why:** the 1.17.0 remote default accepted any unique move on size and mtime alone, which can be fooled by a look-alike. After discussing cheaper checks (head and tail sampling, ssh `sha256sum`) the agreed changes were a size cap on content comparison and group evidence.
- **`hashMaxSize` (D19):** content is compared only for files up to this size (default 2 GiB, `0` = unlimited). Applies to local SHA-256 hashing and to remote rsync-checksum confirmation. Above the cap: default tier accepts a unique move without reading; `verify: hash` skips the file.
- **Folder-move evidence (D20):** for remote sources, pairings are grouped by (old directory, new directory); three or more in a group are trusted without reading. Lone pairings within the cap are confirmed with `rsync -n -c` (one extra rsync run restricted by `--files-from` to just those files). `verify: size-mtime` still trusts everything and reads nothing.
- **Behaviour change:** the remote default now reads lone candidate files (checksum on the remote host's disk, tiny checksums over the wire) where 1.17.0 read nothing. The look-alike case is now rejected by default; it remains possible only with `verify: size-mtime` or for files above `hashMaxSize`.
- **Code:** `select_unverified` decides trust versus confirmation; `Pair.verified` records whether content was compared; `confirm_remote` checks only the lone subset; `Stats` gained `group_supported` and `skipped_large`.
- **Tests (+7; 286 run plus 2 ignored benchmarks):** an isolated remote move is confirmed by default; `size-mtime` reads nothing; a four-file folder move is trusted with no checksum (inode check); two files are not a folder; grouping is by old and new directory together; selection per verify mode and size limit including limit 0; a huge remote file is trusted by default and skipped under `verify: hash`; a huge local file is not read but may be a unique move. The look-alike test now shows the default rejecting it and only `size-mtime` accepting it.
- **Docs:** verification table and bullets in `docs/relocation.md` rewritten, `hashMaxSize` in the settings block, design rationale and the User Guide updated.
- **Decision still open:** whether relocation should default to on (at least for local and cascade sources). Raised in discussion, not changed: it stays off. Phase 6 is to measure the SSH overhead before deciding.

### Follow-up: remote hashing designed (documentation only, no release)

- **The challenge:** a unique vanished/new pairing on size and mtime was described as "safe". It is not proof of identical content. The default (1.18.0 onwards) already confirms lone remote pairings by rsync checksum; the unverified exceptions are folder moves of three or more files, files above `hashMaxSize`, and `verify: size-mtime`. The wording that called these safe or strong evidence was corrected in `relocation.md` and `design-rationale.md`: they are trust decisions, not proofs.
- **The conclusion that proving any set needs remote hashes** is right. It does not require a script: rsync prints the whole-file checksum of every listed file under `-c` with `%C`, even with an empty destination. Probed with rsync 3.5.0: values identical to `md5sum` and `sha1sum` for md5 and sha1; the same through real loopback SSH; hostile file names (leading dash, space, newline, quotes, `$(touch pwned)`, non-UTF-8 byte) hashed correctly with nothing executed; `%B` gives the remote permission bits; `%U`/`%G` are not usable. The probe directory was removed afterwards.
- **`docs/remote-hashing.md`** records the problem, what 1.19.0 does without remote hashes, the findings, the proposed design (candidates by size, one remote rsync run for the new files, the same mechanism locally for old candidates cached in the index, matching by size and hash, safe fallback), what it would change (every remote pairing proven, ambiguous groups recovered, copies detected, 40,000 hashes instead of 20,000 x 20,000 guesses), requirements and a one-line check for a remote host, alternatives and open decisions. It ships in the package.
- **Not decided or built:** the default algorithm, a byte budget, behaviour with an old remote rsync, hashing all folder members versus a sample, and caching. The minimum rsync version for `%C` is set to 3.5.0 on both ends, the only version tested (`--checksum-choice` arrived in 3.2.0); it can be lowered once older releases are tested.

### Follow-ups built (1.20.0, feature)

- **Remote hashing (D24 built).** `match_by_remote_hash` in `src/backup/relocation.rs`: candidates are new files with an old file of the same size and within `hashMaxSize` (at most 32 GiB per run); the source's rsync reports SHA-1 and permission bits for them, the local rsync does the same for the old files of the remaining sizes, and a pairing is made only when size, checksum and permissions agree. Folder moves are no longer trusted as a group, huge files are no longer accepted as unique moves, ambiguous groups of identical size and mtime are recovered, and copies of files that still exist are found. The earlier tiers (`select_unverified`, pairwise `confirm_remote`) remain as the fallback.
- **Fallback.** The local rsync must be 3.5.0 or newer (checked by `rsync --version`). The source's version cannot be read, so it is judged by whether it answers with 40-hex checksums; an error or an empty answer logs the reason, shows it in the report and uses the earlier tiers for that run. `RelocationConfig::remote_hash` is an internal switch the tests use to exercise the fallback; it has no configuration key.
- **Tests (+7 new, 5 reworked):** version, permission and hash-line parsing; a look-alike inside a moved folder is linked under the fallback and rejected with hashes; a huge remote file is not offered with hashes; only files whose size matches an old file are read (nothing is left behind); the confirmation tests (look-alike, permission change, hostile names, partial confirmation) now run against both mechanisms; 300 identical-size renamed files and a remote duplicate are paired by content. The opt-in real-SSH test passes.
- **Measured over loopback SSH (20,000 files):** mass rename of identical-size files copies 5.2 MiB instead of 157 MiB (3.99 s against 0.75 s plain); moved folders 3.11 s (was 2.56 s when trusted), 5.8 MiB.
- **Minimum rsync version fixed at 3.5.0** (the only version tested), as requested; lowering it needs 3.2.x tested first.
- **Report.** `BackupJobReport` gained `relocation`, a one-line summary from `Stats::summary` (files reused and how they were classified, bytes saved, look-alikes rejected, bytes read at the source, skipped or large files, deadline, fallback reason). The Markdown and HTML reports list it under "Moved-file reuse", and `plan_relocation` also logs the fallback reason.
- **Index cost (schema 2).** Publishing no longer rewrites every row: the two row sets are slots `a` and `b` and publish swaps which one is "previous". The replaced rows are cleared when the next run starts filling their slot (`count_files(Current)` is 0 without a current generation row, so they are never reported as current). The scan visits names in order so rows arrive in nearly key order. On 100,000 files: commit 478 ms to 0.5 ms; record plus commit per run 0.98 s to 0.43 s. A database from releases 1.16 to 1.19 (schema 1) has its file and generation rows dropped and rebuilt on first open and keeps its cached hashes; an older release opening a schema 2 database reports it as too new and runs without an index. Recording still touches every file; recording only the changes was judged not worth a larger rewrite at about 4 microseconds per file.
- **Not done:** caching the rsync checksums of old files in the index; a configurable byte budget; real-network and million-file measurements.
